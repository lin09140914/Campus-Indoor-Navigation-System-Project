# 校園室內導航系統：分工與規格 v0.2

> 本文件是全組共用的規格。各組只要照「接口規格」交付，就不必等其他組。
> 規格有疑問或要修改，一律找整合者，並寫進最後的〈變更紀錄〉。
> 標示「建議」的數字是起始值，不是標準答案，試做後可以調整，但要記錄調整的原因。

---

## 1. 專案目標與範圍

**一句話目標：** 在不安裝任何硬體的前提下，讓使用者用 iPhone 的瀏覽器查到工程五館（Engineering Building #5）內「某間房在哪、怎麼走」。

> 註：進度報告原本寫的是數學館；因為新加入的組員都是資工系同學，改做工程五館。見 `docs/decisions.md`。

**第一版（MVP）要做到：**
- 顯示工程五館各樓層平面圖，可切換樓層
- 使用者選起點和房號，系統算出最短路徑並畫在地圖上，包含跨樓層（樓梯或電梯）
- 起點可手動指定

**第二階段（MVP 完成後才做）：**
- 3D 檢視（和 2D 切換）
- 用手機感測器追蹤位置（步數、方向、轉角與樓梯修正）

**明確不做（除非整合者書面同意）：**
- QR code 或任何要在建築內張貼、安裝的東西
- 原生 iOS app（需要 Mac、Xcode、開發者帳號，風險太高）
- Wi-Fi 訊號定位（iOS 一般 app 讀不到）
- 全校園覆蓋，第一版只做工程五館（到現場看過之後，再決定先做哪一層或哪一個區域，不要一開始就做整棟）

**平台前提：** 使用者預設是 iPhone，用 Safari 開網頁。因此：
- 加速度計、陀螺儀、指南針可以讀，但需要 HTTPS，且要在使用者點按之後才能請求授權。
- 氣壓計和 Wi-Fi 訊號在 iOS 網頁讀不到，產品不依賴它們。
- 網頁在螢幕關閉或切到背景時，感測器可能停止（待感測器組驗證），所以導航時要提醒使用者保持螢幕亮著。

## 2. 組別與依賴

人數是對 11 人（整合者 2 人加新成員 9 人）的建議分配，可依實際情況調整。

| 組別 | 建議人數 | 一句話任務 | 主要產出 |
|---|---|---|---|
| 整合組 | 2 | 定規格、整合、品管、文件 | 本文件、倉庫、驗證腳本、每週整合版 |
| 地圖資料組 | 3 | 把工程五館變成資料 | `floor-N.svg`、`graph.json`、`rooms.csv` |
| 圖論路徑組 | 1 | 算最短路徑 | `findRoute()` 模組和測試 |
| UI 組 | 2 | 做使用者看得到的網頁 | 網頁介面（2D 地圖、選單、路徑顯示） |
| 3D 組 | 1 | 做可嵌入的 3D 檢視 | `createViewer3D()` 元件 |
| 感測器與定位組 | 2 | 收集感測器數據、做定位原型 | 數據集、評估報告、定位模組 |

**依賴關係：**

```
地圖資料組 ──(SVG, graph.json, rooms.csv)──► 圖論組、UI 組、3D 組、感測器組（檢查點）
圖論組   ──(findRoute)──────────────────► UI 組
3D 組    ──(createViewer3D)─────────────► UI 組
定位模組 ──(position 輸出)───────────────► UI 組、3D 組
```

**避免互相卡住的原則：** 每個下游組先用整合組提供的**範例資料和假函式（stub）**開發，上游交出真資料後直接替換，程式不用改。

## 3. 共通規範

### 3.1 座標與單位
- 長度單位一律是**公尺**。SVG 的 1 個單位等於 1 公尺。
- 每層樓的原點：建築外框左上角為 `(0, 0)`，`x` 往右（東），`z` 往下（SVG 的 `y`）。
- 3D 世界座標：`x = x`、`z = z`、`y` 向上，`y = (樓層 - 1) × 樓高`。
- 所有樓層共用同一套平面原點，樓梯和電梯在各層的 `(x, z)` 必須相同。
- 樓層用整數：`1`、`2`、`3`，地下室用負數（`-1`）。

### 3.2 命名
- 房號：沿用建築物上的實際房號。本文件與樣板資料用的 `M116` 只是示範，**工程五館的實際房號格式以現場為準**；規格只要求大寫英文加數字、不含空白，若實際房號含符號或空白，請先找整合者調整規則。
- 樓梯與電梯：`STAIR-A`、`ELEV-A`。同一個樓梯井或電梯井在各樓層用**同一個 id**，系統靠這個判斷「是同一座」。
- 節點 id：見 4.2。
- 檔名：英文小寫加連字號，例如 `floor-1.svg`、`graph.json`、`rooms.csv`。

### 3.3 倉庫結構（建議）

```
/data/
  svg/floor-1.svg  floor-2.svg ...
  graph.json
  rooms.csv
  building.json          # 樓高、單位、版本
/src/
  route/                 # 圖論組
  ui/                    # UI 組
  viewer3d/              # 3D 組
  position/              # 定位組
/tools/
  validate-data.js       # 資料驗證腳本（整合組）
/sensor-data/
  raw/                   # 原始數據，不可修改
  processed/
  runs.csv
  marks.csv
/docs/
  spec.md                # 本文件
  decisions.md           # 決策紀錄
```

### 3.4 Git 流程
- `main` 永遠是能運作的版本，**只能經過 Pull Request 合併**。
- 分支命名：`組別/簡述`，例如 `map/floor1-svg`、`route/astar-core`。
- 每個 PR 至少要有一位整合者審核才能合併。
- 提交訊息要看得懂在做什麼（例如「新增 floor-1 的走廊節點」）。
- 原始測量資料和感測器原始數據**不可覆蓋**，要改就新增一份並說明。

### 3.5 「完成」的定義
一件工作算完成，必須同時符合：
1. 產出符合本文件對應的規格。
2. 驗收標準全部通過（各組章節有列）。
3. 有一份簡短說明（怎麼用、已知限制），放在該組資料夾的 `README.md`。
4. 已經合併進 `main`。

### 3.6 會議與決策
- **每週四進度會報**（建議 45 到 60 分鐘），每組約 5 分鐘，只講三件事：做完什麼、卡在哪、下週誰做什麼，並附可展示的東西（連結或截圖）。週五上課時帶著會報摘要和老師討論。詳見第 7 章。
- 一般細節由各組負責人決定；**跨組的規格和範圍由整合者決定**，並寫進 `docs/decisions.md`：

```
## YYYY-MM-DD 標題
- 決定：
- 原因：
- 影響哪些組：
```

- 新想法先放進「待辦清單」，MVP 完成前不排進開發。

### 3.7 技術棧（建議，整合者定案）
- 純網頁：HTML、JavaScript（ES modules），不引入大型框架，讓每個人都讀得懂。
- 3D 用 Three.js；A* 用自己寫的小模組，不引入大型函式庫。
- 部署在 GitHub Pages 這類提供 HTTPS 的地方（iOS 讀感測器需要 HTTPS）。
- 測試：Node 內建的 `node --test` 即可。
- 圖論、定位等純邏輯模組**不可依賴瀏覽器 API**，這樣才能用 Node 做測試和重播。

## 4. 接口規格

這一章是各組之間的「合約」，改動前先通知整合者。

### 4.1 平面圖 SVG（`data/svg/floor-N.svg`）

每層樓一個檔案，`viewBox` 的單位是公尺。

| 元素 | 寫法 | 說明 |
|---|---|---|
| 建築外框 | `<polygon class="outline" points="...">`，只能有一個 | 整層的外輪廓 |
| 房間 | `<polygon class="room" id="M116" points="...">` | 房間範圍，`id` 是房號 |
| 門 | `<line class="door" data-room="M116" x1 y1 x2 y2>` | 門的線段，落在房間牆上，門的中點就是門口位置 |
| 走廊 | `<polygon class="corridor" points="...">` | 只用於顯示，可以多個 |
| 樓梯 | `<polygon class="stair" id="STAIR-A" points="...">` | 各層同一座樓梯用同一個 id |
| 電梯 | `<polygon class="elevator" id="ELEV-A" points="...">` | 同上 |

範例：

```xml
<svg xmlns="http://www.w3.org/2000/svg" viewBox="0 0 40 20">
  <polygon class="outline" points="0,0 40,0 40,20 0,20"/>
  <polygon class="room" id="M116" points="5,1 11,1 11,8.5 5,8.5"/>
  <line class="door" data-room="M116" x1="7.3" y1="8.5" x2="8.7" y2="8.5"/>
  <polygon class="stair" id="STAIR-A" points="36,8.5 39,8.5 39,11.5 36,11.5"/>
</svg>
```

> 注意：最早的範例 `legacy-demo-simple-svg.html` 使用簡化版格式（以矩形加 `data-door` 方向表示門），**不是這份規格的格式，只保留作參考，請勿使用**。開工包裡的 `src/viewer3d/createViewer3D.js` 與 `examples/viewer3d-demo.html` 已改成讀本節的標準格式。

### 4.2 `data/graph.json`

```json
{
  "version": 1,
  "building": "eng5",
  "unit": "m",
  "nodes": [
    { "id": "M116",       "x": 8.0, "z": 4.75, "floor": 1, "type": "room" },
    { "id": "M116#door",  "x": 8.0, "z": 8.5,  "floor": 1, "type": "door" },
    { "id": "F1-C-008",   "x": 8.0, "z": 10.0, "floor": 1, "type": "corridor" },
    { "id": "STAIR-A@1",  "x": 37.5,"z": 10.0, "floor": 1, "type": "stair" },
    { "id": "STAIR-A@2",  "x": 37.5,"z": 10.0, "floor": 2, "type": "stair" }
  ],
  "edges": [
    { "a": "M116", "b": "M116#door", "w": 3.75, "kind": "walk" },
    { "a": "STAIR-A@1", "b": "STAIR-A@2", "w": 8.0, "kind": "stair" }
  ]
}
```

**欄位規則：**
- `type`：`room`、`door`、`corridor`、`stair`、`elevator`、`entrance`。
- 節點 id：房間用房號；門用 `房號#door`；走廊節點用 `F<樓層>-C-<序號>`；樓梯和電梯用 `<井 id>@<樓層>`。
- `kind`：`walk`（走路）、`stair`（樓梯）、`elev`（電梯）。
- **走路邊的 `w` 不得小於兩端點的直線距離**，否則 A* 的啟發式會失準。一般就設成直線距離。
- 跨樓層邊（`stair`、`elev`）的 `w` 是上一層樓所需的等效距離，先用預設值（樓梯 8、電梯 5），之後依實測調整。
- 圖是**無向**的，每條邊只寫一次。

**誰產生：** 地圖資料組。整合組之後會提供一個把 SVG 轉成節點草稿的小工具（尚未產出，見第 6 章），走廊節點仍需人工補上。目前可參考 `tools/gen-sample-data.js` 看節點與邊的組成方式。

### 4.3 `data/rooms.csv`

```csv
room_id,floor,name,type,node_id
M116,1,示範教室 M116,classroom,M116
M201,2,系辦公室,office,M201
```

- `type`：`classroom`、`office`、`lab`、`restroom`、`storage`、`other`。
- `node_id` 對應 `graph.json` 的房間節點。
- UI 的下拉選單和搜尋全靠這份檔案。

### 4.4 `building.json`

```json
{ "id": "eng5", "name": "工程五館", "floors": [1, 2, 3], "floorHeight": 4.0, "unit": "m" }
```

`floorHeight` 要換成**實測值**。

### 4.5 路徑函式 `findRoute`

```js
findRoute(graph, fromRoomId, toRoomId, mode)
// mode: 'any' | 'stair' | 'elev'
// 回傳：
{
  path: [ { id, x, z, floor, type }, ... ],   // 依序經過的節點
  length: 55.5,                                // 總距離（公尺）
  floors: [1, 3],                              // 起點樓層、終點樓層
  via: 'elev'                                  // 'stair' | 'elev' | null（同層）
}
// 找不到路徑，或房號不存在：回傳 null
```

- 這是**純函式**，不碰網頁。
- 起點等於終點時回傳 `path` 只有一個節點、`length` 為 0。

### 4.6 3D 檢視元件 `createViewer3D`

```js
const viewer = createViewer3D(containerElement, { svgs, building });

viewer.setFloor('all' | 1 | 2 | 3);                 // 顯示哪幾層
viewer.setExplode(meters);                           // 爆炸圖間距
viewer.highlightRoom(roomId, 'start' | 'goal' | null);
viewer.showRoute(routeResult);                       // 直接吃 findRoute 的回傳
viewer.setUserPosition({ x, z, floor, confidence });
viewer.onRoomClick(roomId => {});
viewer.dispose();
```

### 4.7 定位模組輸出

```js
const pos = createPositioning(graph);
pos.startAt({ nodeId } | { x, z, floor });   // 起點：使用者選的、或入口
pos.confirm(nodeId);                         // 使用者確認「我在這裡」
pos.reset({ x, z, floor });                  // 手動重設
pos.onUpdate(state => {});                   // 持續回報狀態
pos.feed(sample);                            // 餵一筆感測器數據（重播和即時共用）
pos.stop();

// state：
{
  x, z, floor,
  confidence: 'confirmed' | 'estimated' | 'lost',
  distSinceConfirm: 12.4,    // 距離上次確認已走多少公尺
  ts: 1731300000000
}
```

`feed(sample)` 的格式：`{ t, ax, ay, az, gx, gy, gz, heading }`，單位在 4.8 定義。這樣同一個模組可以拿錄好的數據離線重播，也能接真實的即時感測器。

### 4.8 感測器數據格式

**單位（定案）：**
- 加速度：`m/s²`
- 角速度：`rad/s`
- 方向 `heading`：度，0 為正北，順時針
- 氣壓：`hPa`（僅收集時用）
- 時間 `t`：毫秒，同一次記錄內為相對時間（從 0 開始）

**原始檔 `sensor-data/raw/<檔名>.csv`**（若 app 匯出欄位不同，不要改原始檔，另寫轉換腳本到 `processed/`）：

```csv
t_ms,ax,ay,az,gx,gy,gz,heading,pressure_hpa
0,0.02,9.81,0.10,0.001,0.002,0.000,87.5,1013.20
```

**標記檔 `sensor-data/marks.csv`：**

```csv
run_id,t_ms,event,ref
r001,12340,checkpoint,F1-C-008
r001,48210,stair_start,STAIR-A@1
r001,61200,stair_end,STAIR-A@2
```

`event` 可以是 `checkpoint`、`stair_start`、`stair_end`、`elev_start`、`elev_end`、`turn`。

**檔名：** `日期_人員代號_手機_實驗編號_路線_次數.csv`，例如 `1118_A_iPhone13_E2_corr20m_run3.csv`。

**記錄總表 `sensor-data/runs.csv`：**

```csv
run_id,date,person,phone,placement,experiment,route,true_steps,true_distance_m,notes
r001,2026-11-18,A,iPhone13,hand,E2,corr20m,27,20.0,
```

### 4.9 資料驗證規則（`tools/validate-data.js` 要檢查的）

資料組交件前一定要通過，整合組負責維護腳本。

| 編號 | 規則 |
|---|---|
| V1 | `graph.json` 節點 id 不重複 |
| V2 | `rooms.csv` 的每個房號在 SVG 和圖裡都存在，且圖裡有對應房間節點 |
| V3 | 每個 SVG 房間都有至少一個 `door` 線段 |
| V4 | 邊的兩端節點都存在，沒有重複的邊 |
| V5 | 走路邊的 `w` 不小於兩端直線距離（容許誤差 1e-6） |
| V6 | 每個房間節點都能從入口（或任一指定的基準節點）走到（圖是連通的） |
| V7 | 節點座標在所屬樓層的外框內 |
| V8 | 房間節點在對應房間多邊形內；門節點在房間邊上（容許誤差建議 0.1 m） |
| V9 | 每個樓梯或電梯井在相鄰兩層都有同 id 節點，且 `(x, z)` 相同，並有跨層邊 |
| V10 | 各樓層 SVG 的外框座標系一致（左上角為 `(0,0)`） |

## 5. 各組細節

每組章節的格式：**目標 → 開工前整合者提供什麼 → 怎麼做 → 輸出 → 驗收標準 → 時程 → 卡住時怎麼辦**。

### 5.1 整合組（2 人：整合者與搭檔）

**目標：** 讓其他組不被卡住、產出接得起來。

**分工：**
- 整合者：規格、跨組決策、審核 PR、每週整合、對老師和外部（系辦）。
- 搭檔：品管與文件，維護驗證腳本、會議紀錄、`decisions.md`、各組 README 的完整度；協助申請平面圖。

**要提供給其他組的開工包（見第 6 章）。**

**每週例行：**
1. 週三晚收各組進度與 PR（建議的提交截止時間）。
2. 週四會報前，合併通過驗收的 PR，產生一版可展示的 `main`。
3. 週四會報後整理一頁摘要，週五上課帶去和老師討論。
4. 週五上課後，更新 `docs/decisions.md` 和〈變更紀錄〉，確認下週各組任務。

**驗收標準：**
- 每個組在開工當天就拿到全部輸入。
- `main` 隨時可以打開、展示。

### 5.2 地圖資料組（3 人）

**目標：** 把工程五館變成三份標準檔案：`floor-N.svg`、`graph.json`、`rooms.csv`，先做**一層樓**走通，再複製。

**開工前整合者提供：**
- 本文件第 3、4 章
- 範例 `floor-1.svg`、`graph.json`、`rooms.csv`（假資料）
- 現場測量記錄表（附錄 B）
- 驗證腳本

**怎麼做：**

1. **蒐集來源（同時進行）：**
   - 拍每層的牆上逃生疏散圖。
   - 向系辦申請官方平面圖（整合者協助）。
   - 用 Google 地圖衛星圖量建築外框總長寬，當比例檢查。
2. **現場測量（每層）：**
   - 在走廊一端選固定基準點，量**到每扇門左右邊緣的累計距離**，不要逐段累加。
   - 走廊兩側各量一次，各自記錄，不假設兩側對齊。
   - 房間深度：從門口用雷射測距儀垂直打到後牆，或數地磚。
   - 量走廊寬度、樓梯和電梯位置、樓高、房號。
   - 每個距離量兩次，兩次差大於 10 公分就重量。
   - **閉合檢查：** 走廊寬度加兩側房間深度加牆厚，應約等於建築總寬。差距建議不超過 0.3 m，超過就找出量錯的地方。
3. **畫 SVG：** 用 Inkscape 等工具，依 4.1 的格式，用實測數字（單位公尺）。疏散圖只當底圖，尺寸以實測為準。
4. **建圖：** 依 4.2 列出節點和邊。走廊節點放在每扇門正前方的走廊中線，以及走廊轉角和盡頭。
5. **房間表：** 依 4.3 填 `rooms.csv`。
6. **自我檢查：** 跑 `validate-data.js`，全部通過才交件。

**輸出：**
- `data/svg/floor-1.svg`（之後 2F、3F...）
- `data/graph.json`
- `data/rooms.csv`
- `data/building.json`（含實測樓高）
- 測量原始記錄（照片和記錄表掃描），放 `data/measurements/`
- `data/README.md`：資料來源、誤差、已知問題

**驗收標準：**
- V1 到 V10 全部通過。
- 抽查 5 個距離，和現場重新量的結果差距建議不超過 0.3 m。
- 一層樓所有房間都能從入口走到。

**時程：**

### 5.6 感測器與定位組（2 人）

**目標：** 驗證 iPhone 網頁能做到什麼程度的室內追蹤，並產出可用的定位模組原型。分成兩個角色：

- **角色 S1（數據與評估）：** 收集感測器數據、分析、寫評估報告。
- **角色 S2（定位原型）：** 實作 PDR 加地圖匹配，用 S1 的數據重播驗證。

**開工前整合者提供：**
- 4.7、4.8 的規格
- `position.stub.js`（假模組）
- 手機清單、`runs.csv` 和 `marks.csv` 的空模板
- 地圖組交出一層樓後：節點檔，作為檢查點編號來源

**核心想法（先讀這段）：**
在沒有硬體、iOS 讀不到 Wi-Fi 和氣壓計的前提下，系統**不可能**一開啟就自動知道使用者在哪間教室。做法是：
1. 起點來自使用者選擇，或在建築外用 GPS 偵測到達入口。
2. 之後用加速度計數步、陀螺儀和指南針判斷方向，沿著圖上的走廊移動（地圖匹配：人只會走在走廊上）。
3. 轉彎貼齊轉角節點、爬樓梯貼齊樓梯節點並切換樓層，走到房門口時讓使用者按鈕確認。
4. 任何時候都能點地圖重設。
5. 樓層：偵測到爬樓梯的步態，離開樓梯間時請使用者確認樓層。

**S1：數據收集怎麼做**

| 編號 | 實驗 | 重點 |
|---|---|---|
| E1 | 感測器可用性 | 每支手機：app 和網頁各能讀哪些感測器？記錄手機能力表 |
| E2 | 步數與步長 | 在量好的直走廊（例如 20 m）走，記真實步數和距離，建議每人每支手機 5 次 |
| E3 | 方向飄移 | 走直線和長方形迴圈回起點，記回到原點的位置誤差；標出經過電梯、鋼柱附近的段落 |
| E4 | 樓層判斷 | (a) 網頁可用：爬樓梯的步態偵測準確率；(b) 僅作資料比較：用 app 記錄氣壓，評估如果做原生 app 會多準 |
| E5 | 固定路線評估 | 每層選 3 到 5 條路線，每條走 3 次，在檢查點標記，之後離線算位置誤差（需要地圖組的節點） |
| E6 | 網頁背景行為 | 螢幕關閉、切到背景後感測器是否停止，以及耗電 |
| E7 | 地標偵測 | 轉彎偵測、樓梯偵測的誤報和漏報 |
| E8 | 地圖匹配的效果 | 同一批數據分別「有」與「沒有」貼齊轉角和邊，比較位置誤差 |
| E9（選做） | Android Wi-Fi 訊號 | 前景約每 2 分鐘 4 次掃描，單點至少要停 2 分鐘；只做 1 到 2 個點的小型試測，不進第一版 |

數據標記：檢查點盡量用現有地標（門牌號、樓梯口），不自己在走廊貼東西。每次記錄都在 `runs.csv` 登記一列，標記寫進 `marks.csv`。

**S2：定位原型怎麼做**
1. 步數偵測：對加速度大小做低通濾波與峰值偵測。
2. 步長：用 E2 的結果，先用固定步長。
3. 方向：陀螺儀為主、指南針校正（iOS 網頁取得的方向值）。
4. 地圖匹配：位置表示為「圖上某條邊的第幾公尺」，方向決定走向哪一條邊。
5. 修正：轉彎貼齊轉角、爬樓梯貼齊樓梯並更新樓層、使用者確認時歸零。
6. 實作成 4.7 的 `createPositioning`，純邏輯、不依賴瀏覽器，用 Node 重播 S1 的 CSV 驗證。

**輸出：**

| 產出 | 內容 | 負責 |
|---|---|---|
| 手機能力表 | E1 結果 | S1 |
| 收集流程文件（1 頁） | 怎麼走、怎麼標記、檔名規則 | S1 |
| 數據集 | `sensor-data/` 資料夾，含 `runs.csv`、`marks.csv` | S1 |
| 分析腳本 | 讀 CSV 算指標 | S1 |
| 評估報告 | 步數誤差、平均步長、方向飄移、樓層判斷正確率、各檢查點位置誤差、有無地圖匹配的比較，附圖表 | S1 |
| 參數檔 | 步長、門檻值，供 S2 使用 | S1 → S2 |
| 定位模組 | `src/position/createPositioning.js` 加重播工具和測試 | S2 |
| 平台建議 | 根據 E1、E6：第一版網頁可行與否、是否需要原生 app | S1 |

**驗收標準：**
- 所有 CSV 符合 4.8 的格式，原始檔未被修改。
- 每個評估指標都有樣本數和計算方式，附原始資料位置，可重現。
- 定位模組能用 Node 重播一份真實數據並輸出位置序列。
- **目標值先不訂**，等看過試收集的實際數據後，和整合者一起決定。

**時程：**
- 11/13 到 11/19（第 1 週）：E1、E2、收集流程文件。這幾項不依賴地圖組。
- **12/10 前數據收集結束**，之後只做分析、寫報告和修正定位模組，才來得及在 12/18 前完成評估。
- 之後：E3、E4、E6，地圖組節點到位後做 E5、E7、E8。S2 同步做原型。
- 最後：E9（有時間才做）。

**重要提醒：** 最小版本**不依賴**這一組，這一組的進度不可以拖住主線。

### 7.4 進度落後時：砍範圍順序

5 週很短，12/18 不能延。落後時**從最後一項開始放棄**，並在週四會報上宣布：

1. 最優先保住：**單層（或兩層）的 2D 導航**，也就是 MVP。
2. 其次：多樓層和跨樓層路徑。
3. 再其次：感測器評估報告（有數據支持的說法）。
4. 再其次：3D 檢視。
5. 最先放棄：**即時定位的網頁版整合**（改成「用錄好的數據重播」展示定位原型）。

這個順序是我的建議，請整合者和老師確認，因為它決定了成果發表時你們展示什麼。

## 8. 風險與應對

| 風險 | 應對 |
|---|---|
| 官方平面圖申請不到 | 實測為準，疏散圖當底圖；在資料 README 標明精度 |
| 地圖資料晚交，下游空轉 | 下游一律用範例資料和 stub，格式一致就能直接替換 |
| 規格中途被改，各組做白工 | 規格只由整合者改，且寫進變更紀錄並通知所有組 |
| 人多互相搶改同一個檔案 | PR 流程，每組只改自己的資料夾，合併由整合者審核 |
| 感測器在 iOS 網頁讀不到或背景會停 | E1、E6 優先驗證；以此決定第一版的可行範圍 |
| 手機上 3D 太慢 | 2D 為預設，3D 為選項，可自動退回 |
| 範圍越做越大 | MVP 凍結；新想法進待辦清單，MVP 完成後再議 |
| 只有 5 週，進度落後 | 照 7.4 的「砍範圍順序」從最後一項開始放棄，不延後 12/18 |
| 11/13 才第一次見面，前期空轉 | 11/12 前整合者備妥開工包；見面當天就分組、發任務 |
| 整合者變成瓶頸 | 各組負責人決定組內細節；整合者只管跨組規格和合併 |
