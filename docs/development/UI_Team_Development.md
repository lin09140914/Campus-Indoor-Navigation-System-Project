# 校園室內導航系統 V1 — UI 組開發規格書

**文件版本：** V0.1（草案）  
**負責組別：** UI 組（User Interface Team）  
**適用範圍：** V1  
**狀態：** 待跨組資料規格確認

---

## 1. 開發目標

UI 組負責開發使用者操作介面，整合定位、路徑規劃及 3D 視覺化功能，讓使用者能夠完成室內導航操作。

本組 V1 的核心任務為：

1. **使用者操作介面：** 讓使用者選擇符合統一資料格式的目的地及移動方式。
2. **視覺化功能整合：** 呼叫 3D 組提供的 Function，呈現地圖與導航路線。
3. **例外處理介面：** 接收各組回報的異常狀態，向使用者提供適當的錯誤提示及處理方式。

UI 組是使用者操作及跨組功能協調的主要入口。

UI 組不負責地圖製作、定位演算法、A\* 路徑搜尋或 3D 渲染引擎的內部實作。

| 工作項目 | 交付成果 | V1 要求 |
| --- | --- | --- |
| 使用者操作介面 | 可操作的 Android App UI | 必須 |
| 目的地選擇 | 統一目的地資料的選擇功能 | 必須 |
| 移動方式選擇 | 移動方式選擇介面 | 必須 |
| 定位功能整合 | 取得及使用定位結果 | 必須 |

V1 不要求行走期間的連續導航追蹤或自動重新規劃路線。

## 3. 主要功能與 Function 整合規格

UI 組目前不強制新增獨立的主要對外 Function，而是負責協調已確認的主要功能。

### 3.1 使用者輸入

| 輸入 | 說明 |
| --- | --- |
| 目的地 | 使用者選擇的統一目的地資料 |
| 移動方式 | 使用者選擇的到達方式 |
| 使用者操作 | 定位、搜尋導航及地圖查看等操作 |

### 3.2 getCurrentPosition() 整合

**功能：** 取得定位組輸出的使用者當前位置。

Input 與 Output 依定位組正式 Function 規格。

UI 組負責取得定位結果並提供給後續導航流程，不負責定位演算法。

### 3.3 findRoute() 整合

**功能：** 將導航需求提供給路徑組並取得 Route。

預期輸入：

- Graph。
- 當前位置。
- 目的地。
- 移動方式。

輸出為符合統一規格的 Route。

### 3.4 renderMap() 整合

**功能：** 呼叫 3D 組提供的地圖渲染 Function，將地圖視覺化結果呈現於使用者介面。

預期使用統一 SVG、樓層資料及顯示設定。

### 3.5 renderRoute() 整合

**功能：** 將路徑組產生的統一 Route 提供給 3D 組，於地圖場景上顯示導航路線。

### 3.6 基本操作流程

1. 使用者開啟應用程式。
2. UI 載入或取得必要地圖資料。
3. 使用定位組 Function 取得目前位置。
4. 使用者選擇目的地及移動方式。
5. UI 將資料交給路徑組進行路線規劃。
6. 取得統一 Route。
7. 呼叫 3D 組提供的渲染功能。
8. 顯示地圖與導航路線。
9. 若發生異常，顯示適當的錯誤提示或處理介面。

實際模組調用及資料傳遞方式，後續依系統整合架構確認。

## 4. 統一資料規格

### 4.1 目的地資料

**資料提供者：** 地圖組  
**資料使用者：** UI 組

UI 必須使用統一的目的地資料，不能自行產生與地圖組不一致的目的地 ID。

### 4.2 移動方式

UI 必須提供符合路徑組要求的移動方式選項。

移動方式的正式名稱、代碼及允許值由全專案統一，不得自行定義不同含義。

### 4.3 定位結果

**資料提供者：** 定位組  
**資料使用者：** UI 組

UI 必須能接收統一定位結果，並將位置資訊用於路徑規劃及必要的畫面呈現。

### 4.4 Route 路線資料

**資料提供者：** 路徑組  
**資料使用者：** UI 組、3D 組

UI 必須能接收 Route，並交由 3D 組的渲染 Function 進行視覺化。

### 4.5 樓層與共通識別資料

UI 必須使用統一樓層及地點識別規則，確保目的地選擇、定位結果與地圖顯示一致。

### 4.6 例外狀態資料

UI 必須能區分正常結果與各組回報的異常狀態。

詳細錯誤代碼及資料結構，待統一例外處理規範確定。

本節所有正式欄位及型別，均以全專案統一資料規格為準。

## 5. 跨組交接

| 相關組別 | 交接資料或功能 | 用途 |
| --- | --- | --- |
| 地圖組 | 目的地、樓層及相關地圖資料 | 目的地選擇與地圖資料使用 |
| 定位組 | 定位 Function 與定位結果 | 確認使用者當前位置 |
| 路徑組 | findRoute() 與 Route | 計算並取得路線 |
| 3D 組 | renderMap() | 呈現樓層地圖 |
| 3D 組 | renderRoute() | 呈現導航路線 |
| 各組 | 異常狀態與錯誤資訊 | 顯示對應的例外處理介面 |

各組負責提供可辨識的錯誤狀態，UI 組負責將其轉換成使用者能理解的訊息及操作方式。

## 6. 開發環境與依賴

UI 組以 Android 原生應用程式為目標。

目前技術方向：

- **主要語言：** Kotlin（建議）。
- **UI 框架：** Jetpack Compose（建議）。
- **IDE：** 自由選擇。
- **3D 整合：** 使用 3D 組的 Three.js 視覺化功能。
- **建置環境：** 遵守全專案統一 Android 與 Gradle 版本規範。

Kotlin 與 Three.js 的正式橋接方式，後續依系統整合規範確認。

其他 UI Library 及內部架構由 UI 組自行決定，但必須遵守開發規範。

## 7. 測試與驗收要求

### 7.1 使用者操作測試

| 測試項目 | 驗收方向 |
| --- | --- |
| 目的地選擇 | 使用者能正確選擇目的地 |
| 移動方式選擇 | 選項符合統一移動方式規格 |
| 定位整合 | 能取得並使用定位結果 |
| 路徑整合 | 能傳遞導航需求並取得 Route |
| 地圖顯示 | 能呈現 3D 組提供的地圖 |
| 路線顯示 | 能在地圖上看到導航路線 |

### 7.2 例外處理測試

| 異常情況 | UI 驗收方向 |
| --- | --- |
| 未選擇目的地 | 顯示必要提示 |
| 定位失敗 | 顯示定位失敗資訊及適當操作 |
| 目的地不存在 | 顯示無效目的地資訊 |
| 無可達路徑 | 顯示無法到達的提示 |
| 地圖資料缺失 | 顯示資料不可用的提示 |
| 地圖或路線渲染失敗 | 顯示渲染異常資訊 |

不強制每種錯誤都建立獨立頁面；可依 UX 需求採用提示訊息、對話框或錯誤頁面，但必須確保使用者理解問題及可採取的後續操作。

### 7.3 完整流程測試

至少驗證：

1. 開啟 App。
2. 完成原地定位。
3. 選擇目的地與移動方式。
4. 取得導航路線。
5. 正確顯示地圖與 Route。

此外，也需驗證異常情況不會造成應用程式無法繼續操作。

具體測試工具、測試案例數量及 QA 放行條件，由後續工程規範制定。

## 8. 後續擴充方向

完成 V1 後，可考慮：

- 使用者移動過程中的定位位置更新。

- 更完整的地圖互動方式。
- 使用者介面體驗最佳化。

上述項目不列入 V1 必要驗收。

## 10. V1 完成條件

UI 組完成 V1 必須達成：

1. 提供完整的使用者操作介面。
2. 能接收統一的目的地與移動方式。
3. 能整合定位組的定位 Function。
4. 能整合路徑組的路徑規劃 Function。
5. 能透過 3D 組提供的 Function 顯示地圖及導航路線。
6. 能辨識並處理各組必要的異常狀態。
7. 完成基本導航操作及例外處理測試。
8. 遵守全專案共通資料與開發規範。

UI 組可自主決定內部頁面、元件與輔助函式的設計，但不得自行變更正式跨組資料與介面規格。
