# UI Team Development Specification — V0.1

> 狀態：實作規格草案。跨組資料與函式以 interfaces 規格為準。

## 1. 文件目的與版本
定義使用者操作流程及各組功能的整合方式，確保使用者能選目的地、查看位置、取得並追蹤路線。

## 2. 組別任務與範圍
負責畫面、互動、狀態呈現、權限提示、錯誤訊息與跨組呼叫協調。不負責修改地圖拓樸、定位算法或路徑搜尋核心。

## 3. 使用情境與系統流程
選擇樓層或接受定位（V1 為單棟建築，不提供建築選擇） → 搜尋/選擇 Destination → 呼叫定位與路徑 → 呈現地圖及路線 → 在移動、樓層變更或資料失效時更新 → 提供重試與替代操作。

## 4. 輸入資料與前置條件
接收 Floor、Location、Localization Result、Route、SVG/Graph 及各函式狀態。啟動感測定位前先取得平台權限；顯示名稱可本地化，但 building/location/node ID 不可翻譯或重用。

## 5. 輸出資料與品質要求
輸出使用者操作（目的地、樓層、移動偏好、重試）及可讀的地圖/定位/路線狀態。畫面需區分定位中、成功、低信心、過期、無路徑與錯誤，並提供下一步操作。

## 6. 跨組介面與資料依賴
呼叫 `getCurrentPosition()` 取得位置、以 Location `id` 呼叫 `findRoute()`、`renderMap()` 載入地圖及 `renderRoute()` 疊加路線。呼叫順序須確保 `building_id`、`map_version`、`coordinate_system_id` 相容；UI 不可自行改寫 Route 或把顯示字串當 ID。

## 7. 設計與實作規範
- 狀態流明確，避免重複請求覆蓋較新結果；以時間戳/請求識別判斷回應是否仍適用。
- 目的地依 V1 Location 欄位顯示及選取，以穩定 `id` 傳給路徑組；不自行假設別名欄位存在。
- 地圖可讀性、觸控目標、鍵盤/輔助科技及色彩對比須納入設計；路線不能只用顏色區分。
- 權限用途與感測器狀態以清楚文字說明；失敗時允許手動選樓層或重試（若產品流程支援）。

## 8. 錯誤處理與特殊情況
無權限、無定位、低信心、目的地無效、無路徑、圖資載入失敗及樓層不一致均提供明確狀態與可行動訊息。避免重複提交；取消/過期請求不得覆蓋最新畫面。

## 9. 測試與驗收
走查完整導航流程及權限拒絕、搜尋無結果、無路徑、跨樓層、定位過期、載入失敗、狹窄螢幕與輔助操作。驗證畫面中的位置/樓層/路線與介面回傳資料一致，且使用者可理解失敗原因與恢復方式。

## 10. 交付物、相依與待決事項
交付流程稿、畫面狀態、整合程式、可存取性檢查及端到端驗收紀錄。相依各組介面穩定。待決：目的地搜尋來源、語言清單及視覺設計系統。V1 為 Android 離線 App，見 `System_Architecture.md`。
