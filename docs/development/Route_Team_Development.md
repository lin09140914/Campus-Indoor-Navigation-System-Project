# 校園室內導航系統 V1 — 路徑組開發規格書

**文件版本：** V0.1（草案）  
**負責組別：** 路徑規劃組（Route Planning Team）  
**適用範圍：** V1  
**狀態：** 待跨組資料規格確認

---

## 1. 開發目標

路徑組負責根據地圖組提供的導航圖（Graph）、定位組提供的使用者當前位置，以及 UI 組提供的目的地與移動方式，使用 A\* 演算法計算導航路徑。

本組 V1 的核心任務為：

1. **實作路徑規劃 Function：** 接收 Graph、當前位置、目的地及移動方式，輸出符合全專案統一 Route 規格的導航路線。
2. **完成路徑可行性與正確性測試：** 驗證產生的路徑是否連通、符合移動方式限制，以及是否為目前邊權重定義下的最短路徑。

完成 V1 必要功能後，可進一步研究及最佳化 Graph 的邊權重，以改善路徑規劃品質。

路徑組不負責地圖建構、手機感測器定位、3D 渲染及 UI 開發。

## 2. 工作範圍與交付成果

| 工作項目 | 交付成果 | V1 要求 |
| --- | --- | --- |
| A\* 路徑規劃 | 路徑規劃 Function | 必須 |
| 當前位置與導航圖匹配 | 將定位座標對應至可通行的導航節點 | 必須 |
| 不同移動方式處理 | 支援指定移動方式的路徑搜尋 | 必須 |
| 跨樓層路徑規劃 | 支援樓梯與電梯的跨樓層導航 | 必須 |
| 路徑可行性及正確性測試 | 測試程式與測試結果 | 必須 |
| 邊權重最佳化 | 改善距離或其他路徑成本的計算方式 | 後續選做 |

V1 不要求使用者移動期間的持續追蹤、動態重新規劃或即時避障。

## 3. 主要 Function 規格

### 3.1 findRoute()

**功能：** 使用 A\* 演算法，根據輸入的導航圖與導航需求，計算從使用者當前位置至指定目的地的路線。

**暫定 Function：**

`findRoute(graph, currentPosition, destination, mode)`

### Input

| 參數 | 說明 | 資料來源 |
| --- | --- | --- |
| `graph` | 導航節點、邊及權重 | 地圖組 |
| `currentPosition` | 使用者目前的定位位置 | 定位組 |
| `destination` | 使用者指定的目的地 | UI 組／地圖組資料 |
| `mode` | 使用者指定的移動方式 | UI 組 |

上述參數必須符合全專案統一的資料規格。

其中 `currentPosition` 為定位結果，不要求使用者手動提供起點節點 ID。

### Output

輸出符合全專案統一 Route 格式的導航路線。

預期包含的資訊：

- 路線經過的節點及順序。
- 路線對應的空間座標。
- 路線經過的樓層。
- 路線總距離或成本。
- 必要的跨樓層與移動方式資訊。

具體欄位名稱、資料型態及資料結構，依後續正式統一 Route 規格制定。

### 基本處理流程

1. 接收 Graph、Current Position、Destination 與 Mode。
2. 將當前位置對應至適當的可通行導航節點。
3. 取得目的地對應的導航節點。
4. 根據指定移動方式判斷可使用的邊。
5. 使用 A\* 搜尋路徑。
6. 將計算結果轉換成統一 Route 格式。
7. 回傳路徑結果，供 UI 與 3D 組使用。

### 異常情況

需要能辨識以下情況：

- Graph 資料無效。
- 當前位置無法匹配至可通行節點。
- 目的地不存在或無法對應節點。
- 指定移動方式下不存在可行路線。
- 路徑計算發生錯誤。

詳細錯誤代碼、訊息及回傳方式，後續依全專案例外處理規範統一。

## 4. 統一資料規格

### 4.1 Graph 導航圖

**資料提供者：** 地圖組  
**資料使用者：** 路徑組

Graph 必須符合全專案統一格式。

預期包含：

- 導航節點及位置資訊。
- 節點間的連接關係。
- 邊的權重。
- 樓層及跨樓層連接資訊。
- 通行方式或邊的類型。

路徑組不得自行變更已正式確認的 Graph 格式。

### 4.2 定位結果

**資料提供者：** 定位組  
**資料使用者：** 路徑組

定位結果必須採用統一座標系統，並能讓路徑組判斷使用者所在位置與樓層。

路徑組需將定位結果匹配至可用的導航節點，而不是直接假設定位座標已經位於 Graph 節點上。

### 4.3 目的地與節點對應表

**資料提供者：** 地圖組  
**資料使用者：** 路徑組、UI 組

路徑組必須能透過統一的目的地資料及節點對應關係，找到目的地對應的可通行導航節點。

目的地 ID 與 Graph 節點 ID 不一定相同，必須依照共同資料規格進行對應。

### 4.4 Route 導航路線

**資料提供者：** 路徑組  
**資料接收者：** UI 組、3D 組

Route 必須使用統一資料格式，確保：

- UI 組能接收及處理路線資訊。
- 3D 組能將路線正確疊加在地圖上。
- 路線座標、樓層與 Graph 保持一致。
- 跨樓層路徑能被正確識別。

**本節所有資料的正式欄位、型別與結構，以全專案八項統一資料規格為準。**

## 5. 跨組交接

| 相關組別 | 交接資料 | 用途 |
| --- | --- | --- |
| 地圖組 | Graph、節點對應表 | 建立路徑搜尋所需的導航資訊 |
| 定位組 | 統一定位結果 | 提供導航起點位置 |
| UI 組 | 目的地、移動方式 | 提供導航需求 |
| UI 組 | 統一 Route | 接收規劃結果並控制後續顯示 |
| 3D 組 | 統一 Route | 將路線疊加在地圖上 |

路徑組只負責計算及輸出導航路線，不負責實際的路線繪製。

## 6. 開發環境與依賴

路徑規劃模組應符合全專案選定的 Android 技術架構及共通資料規格。

目前開發原則：

- Android 應用程式以 Kotlin 為建議主要語言，最終依正式技術版本規範。
- IDE 可自行選擇。
- 路徑規劃使用 A\* 演算法。
- 不強制使用外部最短路徑 Library。
- 內部資料結構及輔助函式可由路徑組自行設計。
- 新增依賴必須符合全專案的開發及相容性規範。

具體 Kotlin、Gradle、Android SDK 等版本，以正式開發環境文件為準。

## 7. 測試與驗收要求

### 7.1 路徑可行性測試

| 測試項目 | 驗收方向 |
| --- | --- |
| 同樓層導航 | 能找到符合 Graph 連接關係的路線 |
| 跨樓層導航 | 能透過合法樓梯或電梯邊到達目的地 |
| 不同移動方式 | 產生符合指定通行限制的路線 |
| 節點匹配 | 能合理地將當前位置對應至可通行節點 |
| 路徑合法性 | 路線中的相鄰節點均存在合法連接邊 |
| 無可達路徑 | 能正確辨識沒有可行路線的情況 |
| 非法目的地 | 能正確處理不存在的目的地 |

### 7.2 路徑正確性測試

必須確認 A\* 的輸出符合目前 Graph 的權重定義。

建議至少設計 10 組測試案例，包含：

- 不同起點與終點。
- 多條候選路徑的比較。
- 不同移動方式。
- 跨樓層導航。
- 相同起點與終點。
- 無可達路徑及無效輸入。

使用已知正確答案或獨立計算方式，驗證路線的總權重與最短路徑結果。

### 7.3 測試結果紀錄

每組測試應記錄：

- 使用的 Graph。
- 輸入的當前位置、目的地與移動方式。
- 預期結果。
- 實際回傳結果。
- 是否通過測試。

測試程式與紀錄應能供其他組別或整合組審查。

## 8. 後續擴充：邊權重最佳化

在 V1 功能完成且通過測試後，可考慮改善 Graph 的 Edge Weight。

可能方向包括：

- 根據實際行走距離調整權重。
- 評估樓梯與電梯的移動成本。
- 考慮不同路線的實際通行條件。
- 比較調整權重前後的路徑品質。

若最佳化需要變更地圖組維護的 Graph 資料，必須先與地圖組及整合組協調。

本項目不列入 V1 必要驗收。

## 10. V1 完成條件

路徑組完成 V1 必須達成：

1. 完成 `findRoute()` 路徑規劃 Function。
2. Function 接收 Graph、當前位置、目的地與移動方式。
3. 輸出符合全專案統一 Route 規格的路線。
4. 支援同樓層及跨樓層路徑規劃。
5. 能正確處理不同移動方式及無可達路徑情況。
6. 完成路徑可行性及正確性測試，提交測試結果。
7. 符合專案統一資料規格與開發規範。

邊權重最佳化及移動期間的動態路徑重新規劃，不列入 V1 必要驗收。

其他內部函式、演算法細節及開發工具，由路徑組依專案規範自主決定。
